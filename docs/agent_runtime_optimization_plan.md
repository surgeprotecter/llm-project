# Agent 运行机制优化方案

状态：已实施；两组精简真实功能验收通过。详细实现见 `agent_runtime_implementation.md`，失败记录、用量与局限见 `../output/runtime-upgrade/acceptance.md`。本轮调试成本过高，不作为低成本运行证明。

日期：2026-11-17。文件命名遵循项目的小写 snake_case 规范。

## 1. 目标与范围

围绕 Agent 主循环、上下文构建、外部工具执行、技能加载、旅行规划与报告、状态持久化进行一次连贯调整。

验收目标：正常长任务能够持续推进；已取得结果能够复用；中断后可以从已保存进度继续；局部修改保留无关内容；终端回复与实际产物一致。

保留 LangGraph、SQLite、现有 MCP/CLI/API 接入、标准 HTML 模板和已有可复用业务函数。实现时调整它们的职责与连接方式。

## 2. 已确认的设计决策

| 事项 | 拟采用方案 |
| --- | --- |
| 累计 token | 取消默认 50,000 token 后停止研究的规则，继续记录实际用量。 |
| 固定执行次数 | 取消默认固定规划轮数作为任务终止条件；处理 LangGraph 当前运行步数上限，内部批次边界自动保存并续跑。 |
| 上下文容量 | 保留输入容量监测和输出空间预留，接近工作窗口时压缩，然后继续执行。 |
| 任务规划 | 复杂任务由主模型生成可调整的任务清单；简单对话和单步任务可以直接处理。 |
| 保存粒度 | 工具返回后立即保存；形成一个可复用成果后立即提交；任务状态更新也立即保存。 |
| 语义压缩 | 用独立配置的 deepseek-flash 做增量摘要，原始数据和精确状态仍持久保存。 |
| 执行决策 | 主模型根据当前目标、已完成工作和工具结果选择下一步；旅行报告能力作为工具使用。 |

取消累计用量截断不意味着忽略故障。对工具超时、明确错误、重复无进展进行恢复和调整；任务完成、需要用户提供必要信息、无法恢复的阻塞或用户取消时，才结束当前执行。

## 3. 状态分为四份数据

| 数据 | 内容 | 更新方式 |
| --- | --- | --- |
| 任务清单 | 当前目标、动态拆出的任务、状态、关联结果引用 | 主模型通过计划工具创建和调整，程序校验并立即保存。 |
| 工具记录与证据 | 调用参数、实际返回结果、来源、时间、成功/失败、结果 ID | 执行器在每次调用返回后保存，并关联当前任务。 |
| 可复用成果 | 城市研究结果、选定交通、住宿候选与预算基准、日程、报告版本等 | 业务操作增量提交，同时关联支撑它的证据。 |
| 语义摘要 | 用户选择、重要结论、取舍原因、尚未解决的问题、结果引用 | 在上下文需要整理时由摘要模型更新，版本化保存。 |

### 3.1 最小任务结构

```json
{
  "id": "task_02",
  "description": "研究当前路线中各停留城市的合适体验",
  "status": "in_progress",
  "result_refs": []
}
```

任务状态采用 pending、in_progress、completed。主模型可进一步拆分城市或其他子任务，不要求所有旅行使用相同清单。主模型决定任务是否完成；程序检查结果引用和文件是否确实存在，不因某个工具成功就自动给任务打勾。

整体运行另行记录 running、waiting_for_user、blocked、completed、cancelled，避免把“一轮回复结束”记成“用户任务完成”。

### 3.2 中断恢复

每次工具结果、成果提交、计划更新分别形成可恢复记录。业务状态的版本只在实际修改时推进，读取状态和写 trace 不改变业务状态版本。

同一会话收到“继续”时，恢复原任务目标、计划、用户选择和结果索引，保留完成项。尚未完成的部分继续执行；已完成部分只有在需求变化或结果需要刷新时才重新处理。

已有原始证据但尚未整理的部分，先读取旧证据完成整理。某次调用被打断且无法确认结果时，明确记录为中断，不推断成功。

## 4. 新的主循环

```text
用户输入
  → 恢复任务及成果，纳入用户本轮补充或修改
  → 构建本次上下文；必要时先压缩旧历史
  → 主模型选择：回答、必要追问、更新计划、读取结果、调用技能/工具
  → 执行动作，每项结果及时落盘
  → 主模型根据返回结果决定：提交成果、更新计划或继续查询
  → 重复上述循环
  → 对照当前目标和实际成果检查交付
  → 完成后交付；受阻或需要用户信息时准确说明并保留进度
```

- 当前输入与持续任务目标分开保存。“如何了”用于回答现有进度，不覆盖原任务目标，也不因查询进度而重新查外部资料。
- 主循环不增加一套固定意图分类和业务路由；模型根据目标决定使用什么能力。
- LangGraph 的内部运行批次与用户对话轮次分开。技术批次结束时自动保存、续跑，不让用户重复发送“继续”。
- 进度说明作为执行中的事件显示，不作为任务完成的最终回复。
- 工具参数错误、系统生成的天数分配不一致等，先反馈主模型自行修复或调整方法；只有用户明确约束无法兼容时才提出取舍问题。最终说明由模型结合实际原因生成，不直接透传底层异常。

## 5. 上下文构建与压缩

### 5.1 每次调用主模型的输入

1. 稳定的系统规则、能力目录、技能描述。
2. 当前用户输入与持续任务目标。
3. 用户明确事实、已确认选择、已拒绝选项。
4. 当前计划、必要成果摘要及准确结果引用。
5. 已保存的语义摘要。
6. 最近若干组完整的模型调用/工具返回消息。
7. 当前相关的技能正文和已加载工具 Schema。

详细结果按 ID、任务、城市或报告模块读取。修复当前 evidence 分页只返回一条的问题，提供实际返回数量和明确下一页位置。

对没有变化的同一份状态读取，返回已有结果并提示没有新信息。重复调用检测依据规范化参数及相关业务状态版本，避免把正常的翻页、不同对象查询或主动刷新误判为重复。

### 5.2 压缩的触发与输入输出

触发：预计下一次输入连同所需工具定义、结果空间和输出预留接近配置工作窗口；也可在恢复较长会话时整理旧历史。工作窗口用于安排压缩，不作为任务结束条件。

输入：上一份摘要、尚未被总结的旧消息组、当前任务清单、用户约束/选择、相关成果索引。

输出：关键决定及原因、必要研究结论、未解决问题、结果引用。只总结完整的旧调用组，保留近期调用组和当前必要细节。

结构化状态直接从存储读取，摘要不能覆盖任务状态、日期、价格、用户选择和产物版本。程序检查引用有效性；关键数字和用户约束可回查原记录。摘要失败时保留原数据和旧摘要，尝试恢复，不默默丢弃内容。

这一步是模型语义总结；结果分页、协议配对、大小估算及精确字段保护由程序完成。不会在每个工具调用后都额外请求一次摘要模型。

## 6. 外部工具与技能

### 6.1 查询复用

- 建立跨轮次的结果索引，使用工具名称、规范化参数和必要的会话身份匹配旧结果。
- 参数顺序不同但含义相同的请求视为相同；不同日期、人数、币种等不能混用。
- 同一任务内，条件未变且结果仍适用时复用。用户要求刷新、约束改变、结果过时或旧调用失败时，才重新查询，并记录原因。
- 查询结果与报告消费者共用结果引用。直接查到的航班可以成为报告候选；用户选定后持久保存选择，不要求报告交通操作重新查询一次才能使用。
- 不给每个外部工具再添加 phases、priority、cost 等业务路由参数。

### 6.2 调用执行

- 同批有依赖的查询分轮执行；已明确独立的只读查询可以采用有限并发。
- 保持当前 MCP 长连接及有状态服务的会话要求；同服务需要串行时保持串行。
- 每个调用完成就保存结果；一批执行结束后，按调用 ID 将各结果反馈给主模型。
- 并发主要减少等待时间，不将其宣称为自动减少 token 的办法。

### 6.3 技能加载

- 保留“名称和描述先进入上下文、正文按需加载”的方式。
- 同一任务继续执行时复用已加载内容；当前模型输入只保留相关技能，不反复加载或累加无关正文。
- 旅行技能说明研究方法、来源和产物要求；主模型自行选择任务与调用顺序。

## 7. 旅行规划与报告的调整

### 7.1 操作粒度与结果共用

拆开当前“一次研究所有城市”“一次查询全部交通”等大批处理。支持按城市、交通段、住宿段等对象推进，并保存内部已经形成的成果及未完成位置。

模型决定研究哪些对象、查询哪些工具、何时补查。现有业务函数继续用于资料提取、地点核验、报价规范化、排程、计算和渲染。

增加把已保存证据整理/关联为报告成果的能力。检索工具和报告操作不再各维护一套互不连通的结果。

### 7.2 内容质量要求

这些是报告产物的约束，不是所有用户请求都必须执行的固定流程。

| 内容 | 要求 |
| --- | --- |
| 旅行研究 | 阅读可用笔记正文，保留来源，去重；按用户偏好研究体验，保持地点身份与名称一致。 |
| 多城市覆盖 | 逐城检查研究、住宿、进出交通和日程覆盖，不能只完善前几座城市。 |
| 每日安排 | 完整游览日通常安排 2–3 个适宜主要体验；结合活动时长、抵离、转移和休息调整。餐饮、咖啡、小店融入时间线。 |
| 城际移动 | 给出交通方式、时间依据和费用；无法核实的部分明确标为估算或缺口。 |
| 航班 | 正确区分去程与返程航段、单程/往返、每人与全体价格；往返总价不重复计算。 |
| 酒店 | 每个住宿区域给适量候选，说明日期、房间/人数、每晚与入住总价、优劣和跳转链接。来源有多图时使用已有轮播展示。 |
| 预算 | 每版提供全体与人均区间，包含交通、基准酒店、餐饮及必要预留。缺实查价格时明确采用估算，不把缺报价当作零费用。 |
| 局部修改 | 主模型确定受影响内容，保留其余成果；时间、城市改变后更新必要依赖；报告写出新版本并记录变更。 |
| HTML | 继续使用已经确认的标准模板，内容由结构化成果填充；不能输出未渲染的模板占位符。 |

### 7.3 交付检查

代码检查：日期/天数、时间冲突、价格单位及人数、预算计算、城市/住宿/交通覆盖、结果引用、文件和版本等可确定事项。

模型检查：当前用户目标是否满足、推荐及取舍是否有依据、是否遗漏明确要求、终端说明是否与产物一致。

检查优先返回具体缺口和所需结果引用，主模型定向修复。已有报告不强制本轮再生成报告；普通聊天、解释、比较可直接交付相应回答。

文件可以保存为未完成草稿，但“已完成”必须与实际检查结果一致。受阻时说明完成项、缺口和真实原因，不输出“我继续做”后直接结束。

## 8. 可观测性、取消与旧会话

- CLI 实时显示当前任务、正在执行的工具及简要进度；保留详细 trace 查看能力。
- 记录实际模型输入/输出用量、阶段、缓存命中、结果复用、摘要前后大小和报告版本差异，区分数据预览与完整存储。
- 修复 Ctrl+C 取消与清理路径，保存已完成工作，避免 MCP 线程或子进程清理让退出长时间阻塞。
- 数据库采用增量迁移，先保留原始备份。旧 workspace 可恢复的成果转入新结果索引；从旧执行记录关联已有真实证据。
- 旧记录缺少完成证据时明确保留缺口，不根据工具数量推断任务已完成。不能恢复的整理结果优先基于旧证据重建。

## 9. 实施顺序

1. 状态模型、结果索引与增量保存：先建立可靠的事实基础及旧数据兼容。
2. 主循环与动态计划：取消累计用量/固定次数截断，接入恢复、取消、明确运行状态和进度事件。
3. 结果读取与语义压缩：修复分页，接入 Flash 摘要，保护关键状态与引用。
4. 工具复用和报告连接：接通已有查询到报告的引用，拆分大操作，实现定向修改。
5. 完成精简真实验收，汇总产物、调用记录、实际费用与未解决问题。

实际落地需要同时修改 runtime、gateway、LangGraph 驱动及报告内部调用，避免只去掉外层限制而内部仍被截断。

## 10. 精简真实验收

不运行原有 50 项全量清单；至少两个真实场景，全部使用真实模型、真实工具及真实保存结果。提示词只描述用户需求，不指定工具或内部步骤。

| 场景 | 自然输入与后续操作 | 必须验证 |
| --- | --- | --- |
| A：国内短程单城市、多轮修改 | 从“最近想和朋友出去玩几天，轻松一点，有什么建议？”开始，按实际追问补充信息，选定城市后要求保存攻略；再只更换酒店，最后询问进度或解释。 | 该追问时追问；完整报告；单项修改只触发有关工作；不丢其他数据；状态询问不重新检索；报告版本和实际修改一致。 |
| B：国际长程多城市及恢复 | 复用用户反馈的斯里兰卡 12 天需求，在自然交互中形成方案；研究过程中主动中断一次，恢复后说“继续”；接受某个航班候选后不再次要求确认或无理由重查。 | 多城市均有内容和住宿，城际移动落实；恢复后复用已保存成果；能够继续跨上下文执行；最终 HTML 和预算完整；无固定 token/轮数截断。 |

两个场景中覆盖一次实际语义压缩，可调低测试工作窗口促使压缩，但不能降低内容要求。核对压缩前后的用户约束、选择、计划和结果引用，继续完成同一任务。

已完成并未受改动影响的实查结果可以真实复用，记录来源、查询时间和复用原因；不用 Mock 代替外部结果。

先做针对改动的代码和数据检查，再跑上述真实场景；失败后只重测受影响路径，避免反复从头执行整条长任务。

### 10.1 验收记录

- 每个场景的自然对话、任务清单变化、工具实际调用及复用情况。
- 中断前后的任务和成果快照，证明完成项没有重做或消失。
- Flash 压缩输入输出及关键事实保留情况。
- HTML/Markdown、局部修改前后差异、代码检查与模型审阅结果、桌面/手机页面检查。
- 分阶段实际 token、缓存用量、模型调用次数和外部调用次数。未实测前不承诺具体节省比例。
- 任一核心项失败则记录为未通过并修复，不能用进程退出成功或生成了文件代替通过。
