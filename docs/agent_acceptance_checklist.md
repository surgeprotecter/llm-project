- 后续执行必须使用真实模型和真实外部服务。不得用 Mock、编造报价、伪造笔记或预写答案代替真实结果。

## 2. 执行准备、隔离和结果记录

### 2.1 日期和真实数据

1. 执行时记录香港时区的当前日期。明天、下周、最近等词必须基于该日期解释。
2. 固定报告日期用于可复现地检查跨年和首尾计日。目前采用 2026 年末的未来日期；日期过期后，执行者应同步平移整段日期，保留日数、晚数和跨年关系，并保存实际输入。
3. 铁路实时查询使用执行日次日等实际可售日期；不要把远期无票当作服务故障。超出售票窗口另有专门用例。
4. 不预设某个航班、酒店、价格或目的地必须出现。验收依据为实际结果、来源和约束，不是固定答案。
5. 完整报告测试允许使用合理估算，但必须与已检索报价分开，并注明单位、依据和未知项。

### 2.2 会话和前置条件

- 除明确的连续对话外，每例使用独立用户和旅行会话，避免测试间记忆污染。
- 单个多轮用例内使用同一会话，按实际追问补充，不一次性偷偷填满全部字段。
- 标为“分支”的输入，从同一真实前置状态分别执行，避免上一分支改变另一分支。
- R 类真实报告生成后，可作为 U 类和 G 类的前置状态；复用时记录来源、版本和查询时间。
- 可复制真实会话快照以比较不同分支；必须保留来源，不能把复制状态称为重新执行了一次完整流程。
- 明确要求最新报价的用例，必须发生新的真实查询；复用旧报价不算完成该用例。
- 外部服务预检需要真实查询成功；连接成功、工具发现成功不代表该服务业务可用。

### 2.3 每例记录

每例至少保留：实际 Prompt、多轮消息、前置状态版本、面向用户的输出、实际调用工具及参数、结果或错误、证据来源及时间、前后状态差异、产物路径、输入输出 Token、模型调用次数、耗时、判定和失败原因。日志中的密钥和访问凭证应脱敏。

记录短决策摘要和可观察执行结果即可，不要求记录或展示模型隐藏推理。

建议目录：

~~~text

    tool_trace.json
    before_state.json
    after_state.json

    result.json

~~~

上述为待实现的验收记录规范，不表示当前脚本已经支持这些文件。

### 2.4 判定

| 状态 | 含义 |
| --- | --- |
| NOT_RUN | 尚未执行 |
| PASS | 当前用例的交互、执行和交付要求全部满足 |
| PARTIAL | 有真实有效的部分结果，但未满足完整交付；不能计为完整通过 |
| FAIL | 意图、动作、事实、状态保留或交付存在错误 |
| BLOCKED | 真实服务或环境阻塞，无法验证核心结果；不能算成功 |

故障用例检查的是恢复行为，可以在真实失败条件下通过该故障用例；这不代表相应查询或完整报告成功。

## 3. 通用通过条件

- [ ] 最终输出直接回应当前用户要求，不以“用户想要……”“已有资料足以……”等决策说明代替答案。
- [ ] 只有确实需要用户提供事实或做选择时才追问；系统生成的错误优先由系统修复。
- [ ] 不要求用户知道工具名、机场代码、内部地点 ID、访问令牌或 Schema 字段。
- [ ] 外部事实不足时按需检索；已有信息足够时允许直接回答。
- [ ] 工具调用目标、参数和数据来源正确；不能只检查是否调用了某类工具。
- [ ] 有限次错误恢复之后，明确说明未完成部分；不能把达到循环上限标成完成。
- [ ] 同一工具更换对象或关键词可以再次调用，不能因工具成功过一次就一律阻止。
- [ ] 回答形式符合本轮目标；咨询、比较和解释不会自动生成或更新 HTML。
- [ ] 未要求修改的已确认选择和有效证据保留；必要的连带变化有可解释依据。
- [ ] 不将估算、运营商参考、旧报价或道路时间包装成实时库存和承诺。
- [ ] 记录的是实际进入模型的上下文；候选但被裁掉的工具或证据不能标作已发送。
- [ ] 新一轮用户指令优先于旧计划；旧报告是资料和产物，不是强制流程。

## 4. D 类：日常对话与基础回答（6 例）

### D01 问候

- Prompt：“你好。”
- 预期：自然回应，可简短介绍帮助范围；不索要完整旅行参数表。
- 工具边界：不应发生外部业务调用，不生成报告。
- 失败信号：超出范围、要求先补预算才能聊天、调用机票或酒店、返回内部分析。
- [ ] NOT_RUN

### D02 能力说明

- Prompt：“你能怎么帮我？我还没有确定要不要出去玩。”
- 预期：用用户能理解的语言介绍建议、比较、查询和规划；可以先聊想法，不强迫立刻确定目的地。
- 工具边界：无需外部业务调用；不能宣称已连接的服务一定能查到库存。
- [ ] NOT_RUN

### D03 暂停与普通回应

- 多轮：用户先完成一次候选咨询，再说“谢谢，我先看看，先别继续查了。”
- 预期：简短回应并暂停后续工作。
- 工具边界：该轮外部业务调用为零，不新建报告或修改候选选择。
- [ ] NOT_RUN

### D04 简单计算

- Prompt：“两个人住四晚，每间每晚600元，一间房，住宿一共多少钱？每人分摊多少？”
- 预期：总计2400元，每人1200元；清楚表达一间房和四晚。
- 工具边界：允许本地计算；不查询真实酒店，不生成报告。
- [ ] NOT_RUN

### D05 明确的会话记忆

- 多轮：“我叫小林，这次更喜欢慢慢玩，不想每天换酒店，记住这个。” → “刚才我说我叫什么，旅行节奏喜欢怎样的？”
- 预期：正确复述姓名和偏好；不当作超出旅行范围；不将偏好误解为已预订酒店。
- 工具边界：可以读写会话或用户记忆，无需外部业务调用。
- 说明：跨会话持久化由 G04 单独验证。
- [ ] NOT_RUN

### D06 简单语言任务

- Prompt：“帮我把这句话翻译成英文：我们更喜欢步行，不想每天换酒店。”
- 预期：直接给出准确、自然的翻译。
- 工具边界：不追问出行日期和预算，不检索，不生成报告。
- [ ] NOT_RUN

## 5. E 类：模糊需求、目的地探索与组合（6 例）

### E01 从模糊意愿到候选目的地

- 第1轮：“我最近有空，帮我看看去哪里合适。”
- 第1轮预期：优先澄清影响选择的信息，如从哪里出发、时间窗口与天数、预算范围、国内或国外及偏好；可合并提问，不一次塞进长问卷；不直接查酒店和机票。
- 后续自然补充：“香港出发，两个人，12月中旬有五六天，每人八千人民币以内。国内国外都可以，想暖和一点，看看自然，别太赶。”
- 补充后预期：信息足够做初筛，进行适量真实检索，提供3—5个可比较的国家或城市候选；说明匹配兴趣、时间、交通负担和预算的理由及不利因素。
- 工具边界：目的地研究和必要的交通可达性查询可以触发；不要求先确定酒店，不自动生成详细报告。
- 通过重点：追问能合并用户回答，不重复索要已知事实；候选具有依据和差异，实时价格不得凭空给出。
- [ ] NOT_RUN

### E02 用户不愿提供精确预算

- 第1轮：“想出去玩，但还不想定预算，你先帮我找找方向。”
- 补充：“上海出发，一个人，四五天，喜欢山和徒步，国内就行。”
- 预期：可询问可接受的花费档次；用户仍不确定时，按不同花费或交通负担给出有说明的方向，指出暂不能判断精确预算适配。
- 工具边界：允许检索适合的地区和活动；不能因缺少精确金额而无限追问或停止所有建议。
- [ ] NOT_RUN

### E03 用户已经给足初筛信息

- Prompt：“两个人从广州出发，2026年12月10日至14日，每人6000元以内，想在国内找个暖和、有海又不要太挤的地方。先给我三个方向，简单说优缺点。”
- 预期：直接进行必要研究并给出三个方向；说明季节条件和拥挤度判断依据，不能保证绝对不拥挤。
- 工具边界：不追问已知日期、人数、预算；不自动生成完整攻略、查每个候选酒店或订票。
- [ ] NOT_RUN

### E04 扩展目的地与多个组合

- 前置：已研究过一个国家内的四个地区。
- Prompt：“除了刚才那几个地方，还有哪些值得去？帮我给几种十天以内的组合，我选好了你再做详细安排。”
- 预期：先理解已有候选，再补查至少一个新的有效地区；给出至少三种实质不同的组合、天数分配、兴趣侧重和移动成本；不必遍历全国家。
- 工具边界：允许同一检索工具多次查询不同关键词并读取正文；只按组合可行性做必要交通研究，不自动查询整套酒店或输出详细 HTML。
- 状态要求：新组合保存为候选，不擅自覆盖已确认路线。
- 失败信号：只复述用户诉求、只重排原四个地区、声称有新地点但没有依据、再次机械输出旧报告。
- [ ] NOT_RUN

### E05 只比较，不进行修改

- 前置：E04 已给出组合。
- Prompt：“第二种和第三种哪个更轻松？我不想把假期花在路上，先解释一下，不用改。”
- 预期：围绕两者停留数量、转移次数和已有时间依据比较，给出有条件的建议。
- 工具边界：现有证据够用时零外部调用；不足时只补查决定比较结果的缺口；不更新报告。
- [ ] NOT_RUN

### E06 从探索进入执行，再改变阶段

- 前置：E04 已给出组合，使用连续会话。
- 第1轮：“选第二种，按我们前面说的时间和预算做具体安排。”
- 预期：继承已有事实，明确采用第二种，不重新让用户选择目的地；按缺口完成详细研究和报告。
- 第2轮：“先停一下，我现在不想定了，你先说说还有什么取舍。”
- 预期：本轮切回解释和讨论，停止新增完整规划工作；已存在报告保留，不因存在报告强制再出一版。
- [ ] NOT_RUN

## 6. S 类：单项查询与简单任务（9 例）

### S01 机票查询缺少日期

- Prompt：“香港去东京的机票帮我比较一下。”
- 预期：询问日期或可接受窗口、单程或往返及必要人数；可让用户选择便宜优先或少转机，不索要酒店要求和景点偏好。
- 工具边界：不猜日期查票；不要求用户提供机场代码；可在用户明确接受灵活日期后采用相应查询。
- [ ] NOT_RUN

### S02 真实机票比价

- Prompt：“两个人，香港去岘港，2026年12月10日出发、13日回来。帮我比较便宜一点和飞得舒服一点的选择，先只看机票。”
- 预期：新查真实候选，分别列出去返程机场、当地日期时刻、转机、时长、币种；明确每人单程或往返，以及两人的金额。数据不足的行李或退改规则不猜测。
- 工具边界：必须发生新的真实航班查询；不查酒店、景点和餐厅，不生成旅行报告。
- 数据要求：至少两种可比较候选；真实只有一种或为空时应如实说明，该交付记 PARTIAL 或 BLOCKED，不能虚构第二种。
- [ ] NOT_RUN

### S03 真实高铁比价

- Prompt：“明天两个人从广州南去长沙南，上午出发，帮我比较几趟高铁的时间和二等座价格，便宜和省时间都看看。”
- 预期：解析执行日次日，真实查询班次、时刻、历时、每人票价及两人合计；余票状态注明查询时间。
- 工具边界：铁路工具和必要站点解析；不查机票和酒店，不索要内部站点代码。
- 数据要求：至少两趟真实可比较班次；不足时如实记录，不能将无票改成有票。
- [ ] NOT_RUN

### S04 超出售票窗口

- Prompt：“帮我查2027年1月1日广州南到长沙南的高铁还有多少票。”
- 条件：若该日期执行时仍不在实际售票窗口内，按本例；若已进入窗口，平移到仍未开售的未来日期。
- 预期：解释暂时不能确认实时余票，可提供有日期说明的线路参考或建议接近开售时再查。
- 工具边界：可以核实售票范围；不反复请求同一不可售日期，不把未开售说成售罄，不编造余票。
- [ ] NOT_RUN

### S05 餐厅与咖啡查询

- Prompt：“杭州西湖附近有什么适合两个人吃晚饭的小馆子？别太贵，再推荐两家安静的咖啡馆。”
- 预期：地点足够明确，按合理花费解释“别太贵”，检索餐厅和咖啡候选；列位置、特色、参考花费、适配理由和来源。若人均上限决定筛选，可简短追问或公开采用的初筛范围。
- 工具边界：可用笔记正文、地图和网页信息；不要求完整旅行日期和全程预算，不查询机票和住宿。
- [ ] NOT_RUN

### S06 景点实时信息

- Prompt：“大埃及博物馆现在怎么预约？开放时间和门票怎么收？给我能自己查看的链接。”
- 预期：检索当前资料，优先权威预约和票务来源；区分票种、币种、适用对象和查询时间；冲突资料不能合并成确定事实。
- 工具边界：检索与页面读取即可，不生成整趟旅行报告；不能只凭模型记忆声称是最新规则。
- [ ] NOT_RUN

### S07 附近查询但没有位置

- Prompt：“附近有安静一点的咖啡馆吗？”
- 预期：询问所在城市、街区或地标；解释需要大致位置即可。
- 工具边界：不能默认用户当前位于上一趟旅行目的地、出发地或电脑所在城市；不索要精准住址，不随机搜索。
- [ ] NOT_RUN

### S08 独立酒店筛选

- Prompt：“两个人，2026年12月10日入住岘港、13日退房，一间房，每间每晚800人民币以内，靠海、安静一点。先给我两三家酒店比较。”
- 预期：真实筛选候选；说明入住总价、每间每晚、晚数、币种、已知税费和房型范围；提供跳转链接、优缺点，图片可得时展示。
- 工具边界：酒店与必要区位查询；不要求全程预算、完整路线和出发城市，不自动查航班或生成完整旅行报告。
- 数据要求：未取得范围明确报价时不得声称酒店符合价格上限；不足两家时说明缺口。
- [ ] NOT_RUN

### S09 跨交通方式比较

- Prompt：“两个人下周五从上海去北京，白天出发。高铁和飞机哪个更合适？比较总花费和折腾程度。”
- 预期：结合真实可查班次与报价比较；考虑站点或机场、候车安检、接驳和行李；门到门时间未知时明确采用的市区假设或询问大致出发/目的区域。

### F05 执行预算耗尽、任务尚未完成

- Prompt：“帮我比较几个印尼地区，再给两三种能在十天内走完的组合。”
- 条件：独立验收配置的合理执行预算在真实运行中耗尽；记录实际使用量，避免故意制造昂贵循环。
- 预期：交付已核实的部分结果，说明尚未完成的比较与可继续方向；不以内部决策说明、空报告或“成功完成”结束。
- 状态要求：后续“继续补完刚才的比较”能接续已有有效工作；不能无依据从头重复全部检索。
- [ ] NOT_RUN

## 12. G 类：上下文、反馈循环和扩展性（5 例）

### G01 长会话后仍能处理简单当前目标

- 前置：完成 R04，已有大量真实景点、酒店和交通数据，并进行若干轮自然咨询。
- Prompt：“先别改攻略，给我说说这趟最累的两段在哪里，为什么。”
- 预期：读取相关转移和排程即可回答；不重查全量数据，不生成新报告，不因为旧状态庞大而丢掉当前请求。
- 上下文检查：当前目标、必要工具目录和相关事实实际进入模型；酒店图片、整份报告和无关原始数据不机械重复注入。
- 用量检查：记录实际输入 Token；若一次简单解释仍携带与整份研究状态同量级的输入，必须说明必要性，不能仅以“compacted=True”判通过。
- [ ] NOT_RUN

### G02 同一工具可以围绕新信息继续研究

- Prompt：“先看看印尼适合徒步的地区，再看看适合浮潜的地区，最后告诉我哪些能放进同一趟旅行。”
- 预期：按信息缺口分解研究；若第一次结果不足，允许同一检索工具使用不同关键词或对象继续搜索，并读取相关正文。
- 通过依据：最终同时有徒步、浮潜和组合可行性的依据；不是规定必须调用某工具若干次。
- 失败信号：仅因同一工具已成功就禁止继续检索，或有一次结果便立刻生成无关报告。
- [ ] NOT_RUN

### G03 能力边界与替代方案

- Prompt：“帮我比较开罗到阿斯旺坐火车、大巴和飞机的选择，分别说说适合什么情况。”
- 预期：为不同方式选择适用的真实信息源；国内铁路服务不能用于境外查询。可通过网页资料研究地面交通，但班次参考不能冒充实时座位库存。
- 能力不足时：给出已经核实的部分及缺口，不能为了满足三种方式而编造价格和班次。
- [ ] NOT_RUN

### G04 恢复会话与记忆边界

- 同一会话：生成报告并表达“不喜欢每天换酒店”后退出，再恢复该会话，输入“继续刚才那趟，住的先别改，解释一下交通。”
- 预期：恢复已确认旅行和偏好，回答当前问题，不重新索要全部信息。
- 独立旅行：同一用户新建旅行，输入“这次想去成都三天。”
- 预期：可以适度参考明确记录的稳定偏好，但不能继承上一趟日期、航班、国家或酒店；不同用户不能读取彼此信息。
- [ ] NOT_RUN

### G05 新能力通过注册或 Skill 接入

- 工具子项：选择一个当前未注册且有真实后端的只读能力；只增加适配器/注册或配置，不修改主循环的业务路由。例：若接入日出日落查询，Prompt 为“明天在岘港几点日出？想赶到海边看，应该提前多久到？”
- 工具预期：模型根据能力描述发现并使用工具，必要时先取得真实位置；引用实际结果，普通旅行流程不被强制触发。具体后端和实际 Prompt 在实施验收时锁定并记录。
- Skill 子项：增加“旅行行李清单”技能文件及必要参考，主循环不新增对应分支。Prompt 为“这趟有海边浮潜，也有山里徒步，我只带登机箱，帮我整理一份取舍明确的行李清单。”
- Skill 预期：trace 证明按需加载技能，结合当前旅行及行李约束给实用清单；航空公司具体规则未知时查询或标明待核验，不能编造限额。
- 扩展检查：移除新增能力后，Agent 能识别能力差异或使用合理替代；通用循环不因工具名称变化失效。
- [ ] NOT_RUN

## 13. 必须做的表达变体

以下每组至少执行原用例加一种自然改写。结果语义一致即可，不要求措辞一致，不依赖关键词触发固定分支。

| 对应用例 | 变体1 | 变体2 |
| --- | --- | --- |
| E01 模糊探索 | “最近有几天空，想出去透口气，你帮我拿拿主意。” | “还没想好去哪，能先聊聊吗？” |
| E04 扩展组合 | “这些地方我觉得选择有点少，能再拓展一下吗？先让我挑。” | “别急着排每天，我想先看看还有哪些走法。” |
| U01 住宿修改 | “第二个城市晚上住得再安静些，其他先照原来的。” | “只优化杭州住的，别重新做一遍攻略。” |
| U02 航班升级 | “飞机那块我愿意多花点，时间舒服最重要。” | “先保留酒店和景点，帮我改善一下去回程。” |
| U04 讨论预算 | “多三千的话，你建议提升哪块体验？现在先聊选择。” | “给我几个升级方向，我选完你再查。” |
| Q05 已知信息继承 | 将人数、日期和预算拆成不同轮次补充 | 将同样信息一次给齐，检查是否仍重复追问 |

仅当该变体自身有新的歧义时允许针对性追问；不能通过补全成“完美 Prompt”来掩盖失败。

## 14. 追问专项评分表

| 维度 | 通过要求 | 常见失败 |
| --- | --- | --- |
| 必要性 | 缺少会改变当前行动的重要事实或选择时才问 | 所有请求都索要日期、人数、全程预算 |
| 利用历史 | 使用已提供且仍有效的信息 | 已说4天仍问几天 |
| 提问负担 | 优先问少量影响大的问题，可提供易选选项 | 一次十几项问卷或每轮只问一个机械字段 |
| 任务适配 | 推荐方向允许范围与假设；实时库存需要具体查询条件 | 初筛也强制精确日期，查库存却擅自猜日期 |
| 接续 | 用户补充后更新状态并继续目标 | 每次补充被当作新任务，重新从头问 |
| 矛盾归因 | 区分用户约束冲突和系统生成错误 | 模型分配错天数却要求用户修改正确输入 |
| 用户授权 | 用户允许自行建议后，在边界内推进 | 用户说“你来选”后继续反复问同一选择 |
| 隐私与内部参数 | 只问任务必需的用户事实 | 要求访问令牌、机场代码、Schema 内部字段 |

## 15. 工具、状态和完成条件的专项检查

### 15.1 工具触发

- 正向：S02、S03、S06、S08 必须有对应真实查询；R 类必须有支持各模块的真实证据。
- 反向：D 类、E05和 U04 在已有证据足够时不调用外部业务工具；E03、S05 不因信息表单不全被拦住。
- 精准：U01、U02、U03 按目标对象查询，不能只检查工具类别；应核对城市、日期、人数、航段、住宿段或餐饮区域。
- 有效复用：已有且仍有效的信息可以复用；需要最新价格或条件已经变化时必须重查。
- 计量：分别记录必要调用命中、无关调用、正确参数、有效业务结果；不能用 HTTP 200 或工具次数代替质量。

### 15.2 状态保留

- 对比结构化对象及稳定身份；不能只凭“继承上一版”文字。
- 咨询和候选比较不修改已确认路线。
- 局部修改中，未受影响的酒店、交通、笔记证据和偏好必须保留。
- 条件变化确实使旧数据失效时，标明原因并更新受影响部分；不能为追求“保留率”继续使用错误报价。
- 可以变化的展示字段如生成时间不用于判断业务内容丢失。

### 15.3 正确结束

- 给组合就实际给组合；给报价就实际给候选和口径；给报告就有可打开、内容达标的文件。
- 需要用户选择时，交付足以做选择的信息，再等待；不能只说“可以提供选择”。
- 一次工具成功、JSON 解析成功、达到轮数上限、报告文件写出，均不单独代表任务完成。
- 模型准备结束时检查本轮交付要求；不对每次工具调用无差别增加一轮昂贵评估。

## 16. 用量与执行顺序

1. 先执行日常对话、模糊追问、E04、Q01/Q02 和单项查询，修复基础问题后再运行昂贵报告。
2. 执行5类完整报告，每类使用独立真实会话。保存成功基线，后续修改与长上下文测试按有来源的分支复用。
3. 执行局部调整、恢复和扩展测试；最后补关键表达变体。
4. 每例统计输入/输出 Token、调用次数、外部工具次数与耗时，失败及重试同样计入。
5. 正式执行前确定每批预算和停止阈值；预算不足时暂停并明确未覆盖项，不能降低交付标准或把未运行用例标为通过。
6. 不用固定极小 Token 上限强迫复杂任务提前结束；关注无效重复、大量旧状态、无关工具和反复抽取等可避免的消耗。
7. 不能只报总 Token 降低。应在相同任务质量下对比，至少记录完整规划、单项查询和局部修改三种用量分布。
8. 用户原始自然输入必须保存；调试可改系统策略，不能悄悄把测试输入改成包含工具调用计划的指令再称问题已解决。

## 17. 交付门槛与验收报告

### 17.1 不能出现的严重问题

- [ ] 决策说明被当作最终应答，用户目标尚未完成就结束。
- [ ] 用户明确只咨询/比较，却无理由生成或修改完整报告。
- [ ] 对正确日期和天数抛底层错误，且没有自行恢复或有效澄清。
- [ ] 查询错误城市、国家、日期或航段，仍称为成功。
- [ ] 虚构笔记、价格、图片、库存或预订状态。
- [ ] 未修改内容无依据丢失，或将待选候选写成已确认决定。
- [ ] 上下文裁剪丢失当前请求或必要能力目录，trace 却声称已经发送。
- [ ] 外部阻塞、未执行、部分完成被计入完整成功。

### 17.2 正式交付要求

1. 50个基础用例均有记录和状态；涉及尚未自然出现的故障明确列为未覆盖，不伪造测试证据。
2. 核心功能用例不得有 FAIL 或未执行；外部服务 BLOCKED 必须列出，不能用通过率平均掉。
3. R01—R05 均需实际完成真实报告，满足报告共用清单；它们覆盖的5种形态不能用两个重复城市测试替代。
4. U01、U02、U03、U06 有真实调用增量和快照对比，证明精准修改及必要依赖更新。
5. Q 类、E04、G01、G02 为核心回归，必须满足预期；关键变体也要有实际记录。
6. G05 工具与 Skill 扩展两项均验证，说明接入改动涉及的文件，证明主循环没有新增业务路由。
7. 故障用例中未覆盖项目、服务固有限制和剩余风险单列；若尚未覆盖核心恢复能力，整体标为有条件验收，不能宣称全部完成。
8. 用户可查看至少两份已人工审阅的代表性真实产物：一份短途、一份长途多城市；其余报告同样保留。
9. 页面检查覆盖桌面与手机，并实际检查酒店图片切换。
10. 最终报告必须同时提供结果表、失败与修复记录、证据路径、用量和未覆盖项；“通过”应能追溯到对应输入与运行。
