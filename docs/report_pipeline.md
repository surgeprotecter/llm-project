# 旅行报告研究与修改流程

当前实现已升级为按城市与信息缺口研究、统一每日时间轴和对象级修改。完整说明与自然对话验收见 [自适应旅行规划](adaptive_travel_planning.md)。以下保留价格核验与上下文设计细节。

## 首次生成

真实需求抽取 → 国家/城市识别 → 小红书关键词扩展与混合检索 → 读取笔记正文 → 提取景点和多语言别名 → 按国家、城市、类型核验点位 → 先查往返交通 → 按交通时刻分天并核验道路路线 → 按连续住宿城市查询酒店、补读价格上下文 → 检索餐饮笔记与店铺 → 计算预算区间 → 检查方案完整性 → 固定模板生成 HTML 和 Markdown。

- 国内地点用高德，必须核对服务实际返回的城市和类别，不能把查询参数当成已验证的地点信息。
- 境外地点用 Photon / OpenStreetMap，传国家代码和目的地范围，使用 WGS84；路线由 OSRM 提供，道路模型耗时不代表实时拥堵。
- 地点必须有小红书正文依据；候选不足时补查攻略。短途允许附近一日游，不再用统一30公里阈值删除地点。
- 每天一般2–3个主要景点。飞行与城际转移预留接驳时间；时间冲突和点位不足写入 `quality`，不能把有问题的方案标作通过。
- 餐饮、咖啡、商店与活动进入每日时间轴。全天体验和交通日不机械凑景点数；整日只有短暂停留会触发针对性补查。

## 报告修改

`reports` 表保存完整、不可覆盖的版本快照。修改请求首先加载最新快照，模型判断直接影响的部分，程序按依赖关系扩展修改范围。日期、人数、出发地等差异由程序额外检查。

| 修改 | 直接更新与依赖 |
| --- | --- |
| 调整景点数量 | 每日安排、路线、餐饮就近分配、预算 |
| 某城市换酒店 | 对应住宿段、预算 |
| 增加小吃咖啡 | 餐饮研究、当天餐饮引用、预算 |
| 修改日期/天数 | 日期、每日安排、交通、住宿、预算 |
| 修改人数 | 住宿与交通查询、预算 |
| 修改目的地 | 重新研究对应目的地 |

同一目的地的偏好变化不清空全部证据。没有修改的交通、住宿、攻略结论从快照完整继承，保留检索时间。补查失败时保留旧候选，并明确当前需求是否仍兼容。过期报价、查询失败和用户删除不再用同一个空数组表示。

每版 `revision` 记录基底版本、用户请求、计划修改范围、实际改变与继承的部分；完整模型输入输出由 `--trace-full` 查看。

## 航班与价格

fli 的往返结果把去程和返程展平成一个 `legs` 数组；按方向拆开显示机场、航班、日期与当地时刻。往返组合价不平均拆成虚构单程价格。

为避免 fli v0.9 返回值没有每人/全体价格标识造成歧义，当前查询一名成人的真实往返价格，显示“每人往返参考价”，按旅行人数推算全体参考额并明确标为估算。全体旅客同价、库存、行李与附加费仍需在航空公司复核。

酒店先调用 Booking MCP 搜索；其搜索字段 `pricePerNight` 与 `totalPrice` 可能是同一个数字，`priceIsTotal` 不能单独作为证明。补充只读浏览器工具读取可见价格上下文，程序规则区分卡片上的每晚价、划线原价和入住总价；明确币种、晚数、人数和房间范围才确认住宿总额，并计算每间每晚均价。核价不调用模型。搜索返回的 `imageUrl` 用于酒店图片。缺少明确价格时，展示卡片原文，并在预算中使用标注为规划预留的金额。

## 预算区间

每版展示全体及每人范围，区分真实报价、由报价推算、正文经验参考、规划预留。基准酒店每住宿段只计算一家。餐饮、打车、门票从带原文摘录的笔记价格中提取单位明确的参考；无可靠参考则按目标预算明确分配预留，不能称为商家价格。使用 ExchangeRate-API 的真实汇率及更新时间转换币种，最后计算机动费用和目标预算结余范围。

## 真实验收

```bash
uv run python scripts/live_revision_acceptance.py danang4
uv run python scripts/live_revision_acceptance.py jiangnan7
```

两组均调用真实模型、MCP、API与只读浏览器，不注册 Mock。岘港测试首次生成、调整每天景点数、增加小吃咖啡；苏杭测试首次生成、更换第二段住宿。验收比较前后结构化快照，检查未修改部分保留、点位国家/城市、道路路线、航班双向与人数口径、酒店图片、餐饮来源和预算算术。结果位于 `output/revision-acceptance/`。

补充 API 工具直接通过 HTTP 访问，并在相同工具注册表、证据和 trace 中记录。Photon/OSRM 的公共实例限低频演示使用，均有超时和明确错误，不保证可用性；端点可通过 `TRAVEL_AGENT_PHOTON_URL`、`TRAVEL_AGENT_OSRM_URL` 切换。地图显示 OpenStreetMap 署名。

## 模型上下文与用量

每个模型阶段只收取所需字段。排程输入只有景点ID、名称、城市与坐标，及一个测算交通候选的抵达/返程时刻；不发送图片URL、酒店推广参数、重复航段和全部历史报告。修复上下文只有失败日的点位ID、建议时刻、时长、路段分钟和问题。

景点/餐饮提取使用去重的相关正文片段，原始正文和来源在本地完整保留；费用提取仅发送有价格和单位的片段。酒店计价和预算算术由程序执行。结构化静态提取按精确输入、模型版本、指令和用户计算hash缓存，最长7天；需求、报告修改意图和排程不使用这个缓存。缓存命中在trace记为local_cache_hit，不发API请求；酒店/交通的实时工具查询不受模型提取缓存影响。

模型API返回的真实input_tokens、output_tokens、缓存命中明细写入SQLite的model.usage事件，CLI的--trace显示实际输入输出token。超时未返回用量时不伪造费用统计。400/401/402/403不作无效重试。--trace-full记录具体输入输出；每轮真实验收保留独立run目录，避免后续失败覆盖之前的证据。
